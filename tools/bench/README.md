# 记忆基准评测

把公开数据集灌进临时库，走插件真实的写入校验、召回流水线和注入渲染，分三层出分。

只使用系统临时目录里的库，不解析、不打开真实记忆库。结果写到 `bench-results/`（已忽略，不入库）。

## 快速开始

免 API，几秒跑完（harness-sessions 在相邻的 `dsh-auto-memory` 仓库里）：

```bash
npm run bench -- --data ../dsh-auto-memory/evals/datasets/harness-sessions/standard.json
```

LongMemEval-S（277 MB，不入库）：

```bash
curl -L -o s_cleaned.json https://hf-mirror.com/datasets/xiaowu0162/longmemeval-cleaned/resolve/main/longmemeval_s_cleaned.json
```

```bash
npm run bench -- --data s_cleaned.json --n 30
```

需要 LLM 的跑法，先用 `--dry-run` 看调用次数：

```bash
npm run bench -- --data s_cleaned.json --n 30 --ingest llm --e2e --dry-run
```

确认后设置 `BENCH_API_KEY` 或 `DEEPSEEK_API_KEY`，去掉 `--dry-run` 再跑。LLM 结果按内容缓存到 `bench-results/.cache/`，中断后重跑会接着走，不重复花钱。

本地模型也能跑，`--base-url` 指向 llama-server 的 `/v1`，key 随便填。Qwen3 这类模型要用 `--reasoning off` 启动，否则思考内容会占满判分的 token 额度。小模型当裁判偏松，比较配置时要结合答案级结果看：

```bash
npm run bench -- --data tools/bench/datasets/devmem.json --ingest gold --e2e --base-url http://127.0.0.1:8085/v1 --model qwen3-8b
```

全部参数见 `node tools/bench-memory.mjs --help`。

## 自建测试集 devmem

公开集是英文日常对话，而这个插件面向中文开发场景，所以按 LongMemEval 的方法写了一份同类型的本地测试集。不用下载，也不用 API：

```bash
npm run bench -- --data tools/bench/datasets/devmem.json --ingest gold
```

一位虚构开发者 2026 年 3–10 月的工作记录：55 个手写会话、240 个生成的噪声会话、91 题（77 题有答案，14 题拒答）。`devmem-lite.json` 不含噪声，两份对比能看出记忆库变大的影响。

**题型**沿用 LongMemEval 的七类。**难点标签**可以和题型交叉看：

| 标签 | 测什么 |
|---|---|
| `lexical-gap` | 问法和证据没有共同用词，是留给向量召回的题 |
| `cross-lingual` | 问句和证据语言不同 |
| `task-style` | 用户在下任务而不是提问，回答却要用上记忆 |
| `alias` | 同一事物的别称 |
| `distractor` | 其他项目有相似的值 |
| `short-query` | 很短的问句 |
| `near-topic` 等 | 拒答题的类型：话题相近、张冠李戴、前提不成立、一次性噪声 |

改题后运行 `npm run bench:data` 重新生成。生成前会审计，不通过就不写文件：答案串必须能在证据里找到、不能出现在非证据会话和问句里，拒答词不能出现在任何会话里，`lexical-gap` 和 `cross-lingual` 标签要名副其实。题目出错时分数不会报错，只会悄悄失真。

**局限**：题目是读过插件代码之后写的，难度也是作者定的，不能和公开榜单比，也不能替代公开集。适合比较同一插件的不同版本和配置。噪声由模板生成，240 条里只有 140 条文本不同，比真实记录重复度高。

## 三层指标

| 层 | 怎么测 | 回答什么 |
|---|---|---|
| 检索层 | 直接调 `recall()`，不过门控，不设强度下限 | 证据会话能不能被找到（Recall@k、MRR） |
| 注入层 | 按档位调 `runRecall()` | 证据有没有进上下文，没进的话卡在哪一步 |
| 端到端（`--e2e`） | 带记忆和不带记忆分别作答，用 LongMemEval 官方模板判分 | 记忆对答对题的净贡献 |

**任一证据 / 全部证据**：多会话题要把几条证据都找齐才答得对，所以两个数分开报。

**卡在哪一步**（按流水线顺序取最早的一步）：

- 已注入：至少一条证据进了上下文
- 门控拦：规则门没开
- 没检索到：检索前 `topK` 条里没有证据
- 过滤/预算：找到了，但被强度下限或注入预算挡掉

**拒答题注入**：不该有答案的题仍注入了内容的比例。这些题的历史里常有相关话题，所以它不等于答错，要结合端到端的拒答分一起看。

**答案级**（数据集配了答案串时才有）：比按会话算严格，答案串本身出现才算到手。长会话里命中的可能是不含答案的另一句，这时会话级分数虚高。这一层免 API，但只能确认答案进了上下文，不代表模型答对。需要推算的题，答案串放的是推算所需的原料。

- 只读到旧值：答案没进上下文，过时的值进了，比什么都没注入更糟
- 当复述：含答案的条目被 `isEcho` 判成用户在复述，没有注入
- 被截断：条目选中了，答案被单条字数上限切掉
- BM25 基线：同一批条目上的朴素 BM25（中文二字切分）。两边都低说明题难，只有插件低说明检索有差距

## 档位

所有档位共用同一份写入结果，差异只来自召回配置。

| 档位 | 配置 |
|---|---|
| `default` | 插件默认值 |
| `no-gate` | 只关规则门 |
| `wide` | 关门控、强度下限 0，注入开到配置上限（5 条、2000 字、单条 400 字） |
| `vector` | 默认值加向量召回，需本地向量服务 |
| `vector-wide` | `wide` 加向量召回 |
| `default-h3`、`vector-h3-b700` | 基础档位上只改每轮条数（h）和字数预算（b），用来单独看这两项的影响 |

`default` 和 `wide` 的差距，就是门控与预算损失的部分。向量档位把查询超时放宽到 3 秒，因为这里测的是质量；线上 400ms 的超时会让实际效果更差。

## 写入方式

- `raw`：按句切成不超过 300 字的块直接写入，免 API。关键词取世界内最稀有的词。**这是 runner 的启发式，不是插件行为**，所以 raw 下的门控数字只反映这个启发式。长会话里答案句常和上下文分到不同的块，答案级分数会明显偏低，这类数据优先用 `gold`。
- `gold`：把数据集标注的理想记忆（含已被推翻的旧版本）走真实的 `rememberInto` 写入，免 API。它假设提取完美，用来单独看检索和注入。关键词只从记忆和所属会话机械生成，不看题目，所以比模型写的关键词差，门控和检索分数偏保守。
- `llm`：插件没有自动固化，线上靠模型调用 `mem_remember`。这里把插件自己的工具说明交给模型，一次性产出调用参数，再走真实的 `rememberInto`（校验、去重合并都生效）。

## 时间

`runRecall` 内部用真实时钟算新鲜度，所以写入时把整个世界平移到“最后一题发生在现在”，保留条目之间的相对新旧。否则所有历史条目的新鲜度都是 0。

## 测不到的部分

- **只测被动注入的命中块。** 首轮核心块、项目索引行，以及模型主动调用 `mem_search` / `mem_read` 都不在内。线上模型还能自己查，所以分数偏保守。
- **核心层不覆盖。** `soul/user/rules` 走整段注入而不是召回，`llm` 写入时禁止这几层，用户偏好会写成普通条目。
- **`llm` 写入是近似。** 线上模型在对话中写、看得到索引、被拒收后能改；这里是会话结束后一次写完，被拒收不重试（拒收数会报出来）。
- **证据按会话算。** 会话命中不代表答案没被 180 字的截断切掉，这要看端到端。
- **每题独立。** 会话配额和已注入去重没有被触发。
- **分数不能和官方榜单比。** 官方 judge 是 gpt-4o，抽样也不是全量。适合比较同一 judge 下的不同配置和版本。
